# 喝一杯（Drink One）

## 产品需求文档（PRD v1.0）

# 1. 项目背景

现代年轻人在聚会、独处、观影、游戏、社交等场景下，经常面临：

* 今天喝什么？
* 什么酒适合我？
* 想微醺应该喝什么？
* 聚会应该买什么酒？
* 哪些酒值得尝试？

市面上的酒类应用大多偏向电商或百科。

本产品定位：

> 酒类推荐 + 酒文化探索 + DIY酒谱 + 品鉴记录

而非酒类销售平台。

# 12. 体验修正需求（2026-06-13）

## 12.1 随机抽一杯

问题：

用户点击首页“随机抽一杯”后，弹窗先展示当前酒品，再异步刷新成新酒品，造成视觉跳变。

需求：

* 点击后弹窗先进入抽取中状态。
* 抽取中状态展示进度条或等效进度反馈。
* 抽取完成前不展示最终酒品卡片。
* 抽取完成后再展示酒瓶、酒名、英文名、酒精度、标签、描述、查看详情和再抽一次按钮。
* 云环境不可用时使用本地安全推荐兜底，不直接展示云函数原始错误。

验收：

* 弹窗打开时不会先闪现旧酒品。
* 进度完成后只展示一次最终结果。
* “我想换一杯”同样先进入抽取中状态，再展示新结果。

## 12.2 热门酒谱查看更多

问题：

首页“热门酒谱”的“查看更多”跳转到了 DIY 创建页。

需求：

* “查看更多”应跳转到酒谱排行榜页。
* 排行榜默认展示酒谱相关榜单，而不是进入 DIY 创建流程。

验收：

* 点击“查看更多”进入 `pages/ranking/ranking?type=recipe`。
* 页面标题和 tab 明确表达排行榜语义。

## 12.3 DIY 酒谱提交审核

问题：

DIY 酒谱最后一步点击“提交审核”后缺少明确反馈，且当前 MVP 阶段不再需要审核中步骤。

需求：

* 按钮文案统一为“提交”，不出现“提交审核”“审核中”等文案。
* 点击提交后直接保存到数据库的 `recipes` 集合，创建成功后作为已发布酒谱展示。
* 提交成功后刷新 DIY 页面，默认展示刚刚创建的酒谱。
* DIY 页面默认展示“我的/热门酒谱列表”，不直接进入创建 flow。
* DIY 页面底部固定一个“DIY”功能按钮，点击后再进入创建 flow。
* 云环境不可用时允许进入本地模拟提交成功态，保证 MVP 交互闭环可演示。
* 提交失败时展示短错误文案，不展示底层长错误。

验收：

* 点击提交后有 loading 或状态变化。
* 完成后回到 DIY 列表，刚刚创建的酒谱显示在首位。
* 再次点击不会重复提交。

## 12.4 UI 走查修正

问题：

部分页面与 `f006e823-5deb-4a28-a316-e4c5b34adaad.png` 参考图和 `docs/Codex_UI_Implementation_Spec.md` 存在错位或缺失。

需求：

* 首页、随机弹窗、酒库、酒品详情、DIY、成就、排行榜、我的、设置按参考图走查。
* 保持 iOS 风格、玻璃拟态、浅色主题、柔和阴影、圆角卡片。
* 固定格式 UI 元素需要稳定尺寸，避免文字和按钮错位。
* 表单、弹窗、固定底部按钮必须避开底部 tab 和安全区。

验收：

* 页面主要模块不重叠、不缺失。
* 不渲染自定义模拟状态栏，避免与微信原生状态栏重复。
* DIY 基酒选择为 2 列卡片布局。
* 热门酒谱查看更多只进入酒谱榜，不展示品鉴榜、收藏榜等其它榜单。
* 设置页和详情页底部按钮不贴边。

# 14. 产品完善补充需求（2026-06-16）

## 14.1 首页视觉资产与图标体系重构

### 背景

当前首页部分视觉元素使用了从大图中裁切出来的位图素材，导致图标边缘模糊、风格不统一、与现有浅色玻璃拟态主题不够融合。截图红框区域主要涉及：

* “随机抽一杯”卡片右侧的酒杯/饮品视觉图。
* “热门酒谱”卡片顶部的场景/分类图标区域。
* 页面中用于表达“微醺、小酌、品鉴、聚会”等状态的图标资产。

### 目标

建立统一、可扩展、可替换的图标与轻量插画体系，替换当前裁切图片，提升首页首屏的精致度和专业感。

### 详细需求

* 禁止继续使用从参考图或截图中裁切出的图标、酒杯图、状态图。
* 图标来源优先级：
  1. 使用成熟图标库中语义匹配的 SVG/矢量图标，例如酒杯、杯盏、星光、派对、收藏、榜单、实验瓶等。
  2. 如图标库无法满足主题表达，可使用 `ui-ux-pro-max`、`frontend-design` 或图像生成流程生成同风格原创图标。
  3. 生成图标必须落盘为项目资产，不依赖远程热链。
* 图标风格必须与当前 Drink One 主题一致：浅色背景、橙红到暖黄色品牌主色、玻璃拟态卡片、柔和阴影、圆角、轻量、生活方式感。
* 同一层级图标必须保持统一规格：
  * 状态/分类图标建议使用 44rpx-56rpx 视觉尺寸。
  * 热门酒谱卡片图标建议使用统一容器尺寸，不因图片尺寸不同导致卡片抖动。
  * 所有图标应具备清晰命名，例如 `icon-mood-tipsy.svg`、`icon-scene-party.svg`、`hero-random-cocktail.png`。
* 首页首屏图标不能出现明显像素化、裁切边、白底残留、比例拉伸。
* 图标资产应支持后续主题化，颜色尽量通过统一色板或半透明叠色控制。

### 验收标准

* 红框区域不再引用裁切截图或不完整位图。
* 首页在 375px 宽度设备预览时，图标清晰、不模糊、不越界。
* “随机抽一杯”卡片右侧视觉元素与卡片渐变、文字层级协调，不遮挡 CTA。
* “热门酒谱”列表中每张卡片图标尺寸一致，卡片高度稳定。
* 图标替换后运行 `npm.cmd test` 通过，并补充结构断言防止回退到裁切图。

## 14.2 CloudBase 数据闭环与全量 CRUD 完善

### 背景

当前项目已经具备 CloudBase 基础环境和部分云函数，但产品目标需要完整打通数据闭环：用户在小程序或管理入口中新增、更新、删除数据时，必须真实写入 CloudBase 数据库，而不是依赖本地 mock、fallback 或伪成功状态。

典型目标场景：

* 新增一个酒品后，数据写入 `drinks` 集合，并能在酒库、详情、推荐或管理查询中读到。
* 新增一条品鉴记录后，写入 `drink_records`，并同步用户统计与酒品记录数。
* 创建 DIY 酒谱后，写入 `recipes`，状态按 MVP 策略直接为 `approved`，并能立即在我的酒谱/热门酒谱中展示。

### 目标

完成 CloudBase 数据层、云函数接口、部署脚本、初始化脚本和前端服务层的真实 CRUD 闭环。

### 范围

覆盖以下集合：

* `users`
* `drink_categories`
* `drinks`
* `drink_tags`
* `ingredients`
* `recipes`
* `recipe_likes`
* `recipe_favorites`
* `drink_records`
* `user_favorites`
* `user_achievements`
* `achievement_definitions`
* `recommend_logs`
* `system_configs`
* `report_records`

### 云函数与接口需求

* 保持 CloudBase 环境为 `cloud1-d6gkgmp1a475bc9b5`。
* 所有写操作必须通过云函数执行，前端不得直接写数据库。
* 云函数统一返回 `{ ok: true, data }`；失败时返回 `{ ok: false, message }`。
* 所有用户侧写入必须从 `cloud.getWXContext().OPENID` 解析当前用户身份。
* 禁止前端传入 `_openid`、`openid` 覆盖身份字段。
* 管理类 CRUD 入口必须限制集合白名单和字段白名单。
* `initSeedData` 必须支持：
  * 创建全部 15 个集合。
  * seed 系统数据 upsert。
  * 用户行为集合只建空集合，不写假用户数据。
  * `verifyOnly` 或 `verifyCollections` 返回缺失集合列表。
* 部署脚本必须能一键上传云函数到当前 CloudBase 环境。

### 关键业务流需求

#### 酒品 CRUD

* 支持创建酒品到 `drinks` 集合。
* 支持读取酒品列表、酒品详情。
* 支持更新酒品基础信息、分类、标签、图片、描述、安全风险等级。
* 支持删除或下架酒品；若已有关联记录，优先使用 `enabled=false` 或 `status=hidden`，避免破坏历史数据。
* 新增酒品后，酒库列表和详情页必须能读到该数据。

#### 品鉴记录 CRUD

* 支持新增、列表、详情定位、更新、删除。
* 新增记录时同步 `users.totalDrinkRecord +1` 与 `drinks.recordCount +1`。
* 删除记录时同步递减，并避免出现负数。

#### DIY 酒谱 CRUD

* 创建后写入 `recipes`。
* MVP 阶段创建后 `status=approved`，立即可见。
* 支持我的酒谱列表、详情、更新、删除。
* 删除酒谱时清理 `recipe_likes` 和 `recipe_favorites` 关系。

#### 收藏/点赞/举报

* 酒品收藏写入或删除 `user_favorites`，避免重复关系。
* 酒谱点赞写入或删除 `recipe_likes`，同步 `recipes.likeCount`。
* 酒谱收藏写入或删除 `recipe_favorites`，同步 `recipes.favoriteCount`。
* 举报写入 `report_records`，支持我的举报列表查询。

### 前端行为需求

* 新增、更新、删除失败时必须提示失败，不允许本地伪造成功。
* CloudBase 不可用时可以保留只读 fallback 数据，但写操作不能 fallback 成本地成功。
* 所有写操作按钮必须有 loading/disabled 状态，避免重复提交。
* 错误提示必须是短文案，不展示 CloudBase 原始堆栈。

### 验收标准

* 运行 `npm.cmd test` 输出 `Mini program structure validated.`。
* 部署云函数后，调用 `initSeedData`：`{ "createEmptyCollections": true }` 可创建全部集合。
* 调用 `initSeedData`：`{ "verifyOnly": true }` 返回 `missingCollections: []`。
* 通过管理 CRUD 或酒品新增入口创建一条酒品，能在 `drinks` 集合看到真实记录，并能通过酒库/详情读取。
* DIY 创建酒谱失败时不显示“已保存”，成功时真实写入 `recipes`。
* 品鉴记录新增、更新、删除后，`drink_records` 与相关计数字段保持一致。

## 14.3 热门酒谱跳转与榜单误切换缺陷修复

### 背景

当前存在一个交互缺陷：用户从首页点击热门酒谱进入后，页面中继续点击部分区域会异常切换到另一个榜单。该问题会破坏用户对“热门酒谱详情/酒谱榜单”的路径预期，表现为误触、事件冒泡或榜单 tab 状态被错误更新。

### 目标

修复热门酒谱相关点击路径，确保点击酒谱卡片、酒谱详情区域、榜单页面内容区域时，不会意外切换榜单。

### 详细需求

* 首页热门酒谱卡片点击应进入对应酒谱详情页。
* 首页“更多”入口应进入 `pages/ranking/ranking?type=recipe`。
* 排行榜页面初始 type 为 `recipe` 时，只展示酒谱相关榜单。
* 榜单 tab 切换只能由明确的 tab 控件触发。
* 酒谱卡片内部点击不得冒泡触发榜单 tab 切换。
* 排行榜页面的容器点击、卡片点击、空白区域点击不得修改当前榜单 type。
* 如果当前页面只服务热门酒谱入口，应隐藏或禁用与酒谱无关的榜单切换项，避免用户误入其它榜单。

### 可能原因排查方向

* 检查 WXML 中是否存在父容器 `bindtap` 绑定榜单切换方法。
* 检查卡片内部是否应使用 `catchtap` 阻止冒泡。
* 检查 `data-type`、`data-index` 是否被父子元素复用导致取值错误。
* 检查 `onLoad(options)` 中 `type=recipe` 是否被后续默认值覆盖。
* 检查列表项点击是否误调用 `switchRankingType`、`changeTab` 或同类方法。

### 验收标准

* 从首页点击热门酒谱卡片，进入正确酒谱详情，不切换到其它榜单。
* 从首页点击热门酒谱“更多”，进入 `pages/ranking/ranking?type=recipe`。
* 在酒谱榜单页面点击卡片、图片、标题、空白区域，当前榜单 type 不发生变化。
* 只有点击明确的榜单 tab 控件时，榜单 type 才会变化。
* 修复后补充结构或行为断言，防止误把卡片点击绑定到榜单切换方法。
